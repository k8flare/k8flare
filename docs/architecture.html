k8flare Architecture

kubectl と k3s agent はどちらも CP にだけ話す(kubectl → CP ← agent)。CP から node へ向かうのは pods/log の kubelet 呼び出しだけ。各パッケージの役割とビルド後のサイズも載せる。

Go(WASM / linux)TypeScript(Worker)Durable Object削除候補

1. kubectl / kubelet からリクエストが辿る経路

  1. 認証と TLS。kubectl も kubelet も Bearer トークン。TLS はエッジ(dev では devtls)で終端するので、クライアント証明書は届かない。kubelet の kubeconfig は agent が node:<name>:<password> のトークンで書く。
  2. シェル Worker は 2 分岐のみ。k3s の remotedialer 用 /v1-k3s/connect は WebSocket を受けて放置、残りは全て Loader の apiserver へ。
  3. Loader は sha256 をキーに常駐 Go インスタンスを 1 つ持ち、ASSETS から 25 MiB × 3 のチャンクを結合して起動する。
  4. Go apiserver は upstream の API installer がルーティングし、genericregistry.Store が CRUD を、kine.Storage が DO への読み書きを担う。watch は DO への WebSocket をそのままストリーム応答にする。
  5. DO への経路。loader.ts が factory で CLUSTER.get("default") の stub を dynamic worker の env に STORAGE として渡し、Go は bridge.BindingTransport{Name: "STORAGE"} でそれを fetch する。旧リポジトリの S2 は DO namespace が渡せないことしか示しておらず、stub は渡せた(2026-09-13 実測、wrangler dev)。

2. ClusterLoopback は外した

自分自身への service binding と WorkerEntrypoint は削除。dynamic worker の env に渡した DO stub は、isolate の寿命にわたる別々のリクエスト(CRUD、5 分単位の watch WebSocket、agent の join)からそのまま使えた。未検証 本番 workerd での同挙動。dev と本番で Loader の env 検証が異なる場合はここが最初に壊れる。

5. どこを削れるか

wasm_exec.js のパッチ(scripts/wasmpack exec)

Go 側 bridge の context 依存 + JS Proxy

常駐インスタンスは env を毎 dispatch で受け取るので、起動時の context は不要。bootstrap が globalThis.k8flare = {binding, ready} を置けば upstream の wasm_exec.js を無改変で使え、wasmpack exec と Proxy が消える。実装 1 時間・低リスク

pods/log の plain-HTTP 経路(agent の --kubelet-plain-port)

agent 15 行 + KUBELET_SCHEME/PORT

dev 専用の回り道。k3s トンネル(/v1-k3s/connect)のサーバー側を Go で持てば本来の経路になるが、remotedialer 実装が要る。今は削らず、経路を 1 本にする側で解消。

scripts/devtls

Go 150 行、dev 専用

wrangler dev --local-protocol https で置き換えられる可能性。CA を VM に配る手順は残る。未検証。

削れないもの

チャンク化(ASSETS 25 MiB 上限)、mirror のオーバーレイ 5 件(etcd factory・OTLP exporter・CEL・installer の hub version・k3s の kubeconfig フック)、supervisor の 9 エンドポイント(k3s agent が要求)。
