k8flare Architecture

kubectl と k3s agent はどちらも CP にだけ話す(kubectl → CP ← agent)。CP から node へ向かうのは pods/log の kubelet 呼び出しだけ。各パッケージの役割とビルド後のサイズも載せる。

Go(WASM / linux)TypeScript(Worker)Durable Object削除候補

1. kubectl / kubelet からリクエストが辿る経路

  1. 認証と TLS。kubectl も kubelet も Bearer トークン。TLS はエッジ(dev では devtls)で終端するので、クライアント証明書は届かない。kubelet の kubeconfig は agent が node:<name>:<password> のトークンで書く。
  2. index.ts は 2 分岐のみ。/v1-k3s/connect はノードトークンを検証してから、そのノード専用の NodeTunnel Durable Object(NODE_TUNNEL.idFromName(nodeName))へ WebSocket アップグレードごと渡す。残りは全て apiserverFetch() が読み込む apiserver(front)dynamic worker へ。別に scheduled() が Cron Trigger(毎分)から SCHEDULER.poke() と CONTROLLERS.poke() を呼ぶ — 書き込みが無くても nodelifecycle の NotReady 判定や workqueue の再試行、CronJob のスケジュールを進めるため。
  3. front(apiserver)は認証(AdminToken + NodeToken の union)と supervisor(join プロトコル)をマウントし、/api・/apis の root discovery をまとめる。実際の CRUD は自身では持たず、APIGROUPS(/api, /apis/<group> → apiserver-<group>)・CUSTOMRESOURCES(未登録グループ、および /apis への CRD グループのマージ)・OPENAPI(/openapi/*)という 3 本の self Service Binding へストリーム転送する(X-Remote-User 付与)。本番実測(k8flare.kooffice.workers.dev, 2026-09-15): discovery が全グループを順に叩くと 28–43MB のモジュールが複数、同一 isolate に載る。Worker Loader の 64MiB code cap は個々に守っていても、128MB の isolate memory cap をまとめて超える(1,544 イベント中 98 exceededMemory・101 例外、すべて discovery 経由)。wrangler dev はこの cap を強制しないためローカルでは再現しない。
  4. apiserver-<group>は installer → genericregistry.Store → kine.Storage という同じ配線を、自分のグループの型だけリンクして持つ。全グループ共通で Terminating な namespace への create を上流 NamespaceLifecycle と同じ Forbidden で拒否する。core だけ pod の graceful delete・namespace の Terminating 遷移と finalize・namespace 初期化・pods/log があり、pod 作成/更新で Spec.NodeName が空なら SCHEDULER.poke()、他の書き込みでは CONTROLLERS.poke()(kube-controller-manager の 16 コントローラーを workqueue が空になるまで回す)を呼ぶ。テーブル整形は PRINTERS.convertToTable(group, object) の RPC。pods/log 等の kubelet アクセスは KubeletProxy が TUNNEL binding(NodeTunnels → 該当ノードの NodeTunnel DO)経由でノードに直接ダイヤルせず届ける。
  5. scheduler は poke() で起こされ、waitUntil の窓の間だけ実 kube-scheduler の informer とスケジューリングループを回す。読み書きは自分では持たず APISERVER binding(= front と同じエントリポイント)を再入呼び出しする。
  6. DO への経路。front・各 group DW・customresources はそれぞれ独立に env.CLUSTER.get(idFromName("default")) の stub を STORAGE として受け取り、Go は bridge.BindingTransport{Name: "STORAGE"}(watch は bridge.DialWebSocket)でそれを叩く。openapi・scheduler・printers-<group> は STORAGE を持たない。

2. ClusterLoopback で外したのは DO 中継専用の 1 本だけ

削除したのは Cluster DO のスタブを渡すためだけにあった自己 WorkerEntrypoint。今は index.ts / APIGroups / CustomResources がそれぞれ env.CLUSTER.get(idFromName("default")) で直接スタブを作り、loadWasmWorker() の env に STORAGE として渡す。一方、グループ別 DW を呼び分けるための自己 Service Binding(APIGroups / CustomResources / OpenAPI / Printers / Scheduler、表 3 参照)はこれとは別物で、今回の分割の中心として残っている。未検証 本番 workerd での同挙動。dev と本番で Loader の env 検証が異なる場合はここが最初に壊れる。

5. どこを削れるか

wasm_exec.js のパッチ(scripts/wasmpack exec)

Go 側 bridge の context 依存 + JS Proxy

常駐インスタンスは env を毎 dispatch で受け取るので、起動時の context は不要。bootstrap が globalThis.k8flare = {binding, ready} を置けば upstream の wasm_exec.js を無改変で使え、wasmpack exec と Proxy が消える。実装 1 時間・低リスク

(解消済み)agent の --kubelet-plain-port

node-tunnel 実装で削除済み

node-tunnel(remotedialer サーバーを Go/wasm で NodeTunnel DO に載せたもの)が入り、KubeletProxy は TUNNEL binding 経由に切り替わった。agent 側の --kubelet-plain-port と apiserver 側の旧 KUBELET_SCHEME/KUBELET_PORT は実際に削除済み。kubelet への TLS クライアント証明書配布はまだ未接続で、当面は admin token を無検証 TLS で代用。

scripts/devtls

Go 150 行、dev 専用

wrangler dev --local-protocol https で置き換えられる可能性。CA を VM に配る手順は残る。未検証。

削れないもの

チャンク化(ASSETS 25 MiB 上限)、mirror のオーバーレイ 15 件(apiserver 4・client-go 8・apiextensions/component-base/kubernetes 各 1。etcd/gRPC egress/APF を外す factory 系と、ワーカーごとに自グループだけリンクさせる clientset・informer scheme の刈り込みが中心)、supervisor の 9 エンドポイント(k3s agent が要求)。
